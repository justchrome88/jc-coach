# Дополнение к ТЗ: отслеживание выполнения рекомендаций AI-тренера

## 1. Суть идеи

В проект CS2 Personal Coach нужно добавить систему не просто генерации рекомендаций, а отслеживания их выполнения по следующим матчам.

AI-тренер должен уметь:

1. Найти проблему игрока.
2. Сформулировать конкретную рекомендацию.
3. Закрепить её как активную тренировочную цель.
4. После каждого нового матча проверять, стало ли лучше.
5. Показывать игроку, выполняет ли он рекомендацию.
6. Подсвечивать матчи зелёным/жёлтым/красным по прогрессу.
7. Объяснять, почему матч считается успешным или провальным относительно цели.

Главная ценность: игрок видит не просто статистику, а связь между советом тренера и реальным изменением поведения.

Пример:

Тренер сказал:
> “Не умирай первым. Снизить early deaths и entry deaths. Играть первые 30 секунд раунда осторожнее, не брать дуэли без размена.”

После следующих матчей система проверяет:
- стало ли меньше entry deaths;
- снизились ли early deaths;
- вырос ли KAST;
- уменьшились ли deaths per round;
- вырос ли survival rate;
- не просел ли при этом impact/ADR слишком сильно.

Если динамика положительная — матч/период подсвечивается как прогресс.

---

## 2. Почему это важно

Обычные аналитические сервисы показывают метрики. Но игрок часто не понимает:

- что именно делать;
- выполняет ли он совет;
- становится ли лучше;
- какой матч был хорошим с точки зрения тренировки, даже если команда проиграла.

Эта фича превращает продукт в персонального тренера.

Не просто:
> “K/D 1.06.”

А:
> “Сегодня ты выполнил главную цель: entry deaths снизились, KAST вырос, ты реже отдавал первый фраг. Даже при поражении матч полезен для прогресса.”

## 3. Основные сущности

### 3.1 Coach Recommendation

Активная рекомендация тренера.

Поля:

- `id`
- `user_id`
- `title`
- `description`
- `category`
- `status`
- `priority`
- `created_at`
- `started_at`
- `ended_at`
- `target_period_matches`
- `baseline_period_matches`
- `baseline_metrics_json`
- `target_metrics_json`
- `success_rules_json`
- `failure_rules_json`
- `coach_comment`
- `created_by`
- `updated_at`

### Возможные категории

- `survival`
- `entry_duels`
- `utility`
- `positioning`
- `trade_teamplay`
- `map_specific`
- `ct_side`
- `t_side`
- `aim_duels`
- `clutch`
- `economy`
- `discipline`

### Возможные статусы

- `active`
- `paused`
- `completed`
- `failed`
- `archived`

---

### 3.2 Match Recommendation Evaluation

Оценка конкретного матча относительно активной рекомендации.

Поля:

- `id`
- `recommendation_id`
- `match_id`
- `evaluated_at`
- `score`
- `status`
- `evidence_json`
- `positive_signals_json`
- `negative_signals_json`
- `coach_comment`

### Статусы оценки матча

- `green` — рекомендация выполнена/есть явный прогресс.
- `yellow` — смешанный результат.
- `red` — рекомендация провалена.
- `gray` — данных недостаточно.

---

### 3.3 Recommendation Progress Summary

Сводка прогресса по рекомендации.

Поля:

- `id`
- `recommendation_id`
- `period_start`
- `period_end`
- `matches_count`
- `green_count`
- `yellow_count`
- `red_count`
- `progress_score`
- `baseline_comparison_json`
- `summary_text`
- `created_at`

## 4. Пример рекомендации

```json
{
  "title": "Снизить количество первых смертей",
  "description": "Не пикать первым без размена, играть первые 30 секунд раунда осторожнее, не отдавать entry death.",
  "category": "survival",
  "priority": "high",
  "baseline_period_matches": 15,
  "target_period_matches": 10,
  "baseline_metrics": {
    "entry_deaths_per_match": 3.2,
    "early_deaths_per_match": 4.1,
    "kast": 72.0,
    "deaths_per_match": 18.5
  },
  "target_metrics": {
    "entry_deaths_per_match": "<=2.4",
    "early_deaths_per_match": "<=3.2",
    "kast": ">=74.0",
    "deaths_per_match": "<=17.0"
  },
  "success_rules": [
    "entry_deaths_per_match decreased by at least 15%",
    "early_deaths_per_match decreased by at least 10%",
    "kast did not decrease",
    "adr did not decrease by more than 10%"
  ],
  "failure_rules": [
    "entry_deaths_per_match increased",
    "early_deaths_per_match increased",
    "kast dropped below baseline by more than 3%",
    "player became too passive and adr dropped by more than 15%"
  ]
}
```

## 5. Логика оценки матча

Для каждого нового матча после создания активной рекомендации система должна:

1. Найти все активные рекомендации.
2. Рассчитать метрики матча.
3. Сравнить их с baseline.
4. Применить success/failure rules.
5. Присвоить статус:
   - green;
   - yellow;
   - red;
   - gray.
6. Создать короткий комментарий тренера.

### Пример

Активная рекомендация:
> “Снизить первые смерти.”

Новый матч:

```json
{
  "map": "Mirage",
  "entry_deaths": 1,
  "early_deaths": 2,
  "kast": 78,
  "adr": 82,
  "deaths": 15
}
```

Вывод:

```json
{
  "status": "green",
  "score": 86,
  "positive_signals": [
    "entry deaths ниже baseline",
    "early deaths ниже baseline",
    "KAST выше baseline",
    "ADR не просел"
  ],
  "negative_signals": [],
  "coach_comment": "Хороший матч по главной цели. Ты реже отдавал первый контакт и не потерял impact. Продолжай тот же стиль ещё 5 матчей."
}
```

## 6. Визуализация в интерфейсе

### 6.1 Блок активных рекомендаций на Dashboard

Показывать:

- название рекомендации;
- статус;
- прогресс за последние N матчей;
- baseline;
- target;
- количество зелёных/жёлтых/красных матчей;
- комментарий тренера.

Пример:

```text
Главный фокус: не отдавать первый фраг

Прогресс: 6/10 матчей засчитаны как успешные
Entry deaths: 3.2 → 2.1
Early deaths: 4.1 → 2.9
KAST: 72% → 75%
Статус: движешься верно
```

### 6.2 Список матчей

В таблице матчей добавить колонку:

- `Coach Goal`

Цвета:

- зелёный — матч помог прогрессу;
- жёлтый — нейтрально/смешанно;
- красный — провал по цели;
- серый — недостаточно данных.

Пример:

| Дата | Карта | Результат | K/D | ADR | Coach Goal |
|---|---|---:|---:|---:|---|
| 2026-07-01 | Mirage | Win | 1.24 | 84 | 🟢 |
| 2026-07-02 | Ancient | Loss | 0.91 | 67 | 🔴 |
| 2026-07-03 | Dust2 | Win | 1.10 | 78 | 🟡 |

### 6.3 Страница рекомендации

Для каждой рекомендации сделать отдельную страницу:

`/recommendations/{id}`

Показывать:

- описание цели;
- baseline;
- target;
- графики метрик;
- список матчей;
- комментарии по каждому матчу;
- общий вывод;
- кнопки:
  - “завершить цель”;
  - “продлить цель”;
  - “сделать главной целью недели”.

## 7. Rule-based MVP без сложного AI

В первом варианте можно сделать всё без AI.

### Рекомендация: снизить entry deaths

Метрики:

- `entry_deaths`
- `early_deaths`
- `kast`
- `deaths`
- `adr`

Green если:

- entry_deaths ниже baseline;
- early_deaths ниже baseline;
- KAST не ниже baseline;
- ADR не упал критично.

Red если:

- entry_deaths выше baseline;
- early_deaths выше baseline;
- KAST ниже;
- ADR сильно ниже.

Yellow если смешанный результат.

---

### Рекомендация: повысить utility impact

Метрики:

- `utility_damage`
- `flash_assists`
- `enemies_flashed`
- `unused_utility_at_death`, если доступно;
- `adr`

Green если:

- utility_damage вырос;
- flash_assists/enemies_flashed выросли;
- ADR не упал.

Red если:

- utility_damage низкий;
- flash assists = 0;
- игрок умирает с большим количеством неиспользованных гранат.

---

### Рекомендация: улучшить слабую карту

Метрики:

- map winrate;
- map K/D;
- map ADR;
- T-side winrate;
- CT-side winrate;
- early deaths by map;
- utility by map.

Green если:

- на целевой карте улучшились 2–3 ключевые метрики;
- даже при поражении игрок сделал меньше старых ошибок.

## 8. AI-уровень

AI должен использовать recommendation tracking так:

1. Создавать рекомендацию не абстрактно, а как измеримую цель.
2. Объяснять, какие метрики будут использоваться.
3. После каждого периода давать вывод:
   - цель выполняется;
   - цель частично выполняется;
   - цель не выполняется;
   - цель выбрана неправильно;
   - данных недостаточно.

### Prompt-фрагмент для создания рекомендации

```text
На основе анализа матчей создай одну главную тренировочную рекомендацию.

Требования:
1. Рекомендация должна быть измеримой.
2. Укажи baseline metrics.
3. Укажи target metrics.
4. Укажи success rules.
5. Укажи failure rules.
6. Укажи, сколько матчей нужно для проверки.
7. Не создавай рекомендацию, если данных недостаточно.
```

### Prompt-фрагмент для оценки прогресса

```text
Оцени прогресс игрока по активной рекомендации.

Данные:
- рекомендация;
- baseline metrics;
- target metrics;
- последние матчи;
- evaluations по каждому матчу.

Верни:
1. выполняется ли рекомендация;
2. какие метрики улучшились;
3. какие ухудшились;
4. не стал ли игрок компенсировать проблему неправильным способом;
5. продолжить цель, завершить или заменить.
```

## 9. Важная защита от ложного прогресса

Система не должна считать прогрессом ситуацию, где игрок просто стал пассивнее.

Пример:

Рекомендация:
> “Не умирать первым.”

Плохой ложный прогресс:
- entry deaths снизились;
- но ADR сильно упал;
- impact упал;
- команда проигрывает больше;
- KAST не вырос.

Вывод:
> “Ты стал меньше умирать первым, но потерял влияние на раунд. Это не полноценный прогресс. Нужно играть дисциплинированнее, но не прятаться.”

Это критично для качества тренера.

## 10. Acceptance Criteria для MVP этой фичи

Фича считается реализованной, если:

1. Можно создать активную рекомендацию вручную или автоматически.
2. У рекомендации есть baseline и target.
3. После импорта нового матча система оценивает матч относительно рекомендации.
4. В списке матчей виден цветовой статус выполнения.
5. На dashboard видно, выполняется ли главная цель.
6. Есть страница рекомендации с прогрессом.
7. Система умеет отличать настоящий прогресс от ложного пассивного улучшения хотя бы по простым правилам.
8. Coach report учитывает активную рекомендацию.

## 11. Минимальная реализация для ближайшего MVP

Если нужно сделать быстро, реализовать только:

1. Таблицу `coach_recommendations`.
2. Таблицу `match_recommendation_evaluations`.
3. Одну встроенную рекомендацию:
   - “Снизить первые смерти”.
4. Оценку матчей по entry_deaths/kast/adr.
5. Колонку статуса в `/matches`.
6. Блок на dashboard:
   - active recommendation;
   - progress;
   - last match status.

Этого достаточно, чтобы проверить ценность идеи.
