# ТЗ: жизненный цикл CS2 demo

## Цель

Целевая схема для продукта: демка `.dem` нужна как временное сырье. Система должна скачать demo, извлечь все нужные данные, сохранить проверенный parsed payload и затем удалить raw `.dem`, чтобы не копить гигабайты файлов.

На текущем этапе raw `.dem` не удаляем, потому что набор конечных метрик и raw-срезов еще не утвержден. Но архитектуру строим именно под будущий режим `download -> parse -> verify -> delete raw`.

## Текущее ограничение

- Серверный раздел `/` сейчас на `ext4`.
- Прозрачного filesystem-сжатия на текущем разделе нет.
- Если оставить исходные `.dem` и рядом создать `.gz`/`.zst` копии, место на диске временно вырастет, а не уменьшится.
- Поэтому текущий этап не должен создавать тяжелые архивные копии и не должен удалять исходные `.dem`.

## Целевой pipeline

1. Получить share code.
2. Скачать `.dem.bz2` у Valve и распаковать во временный `.dem`.
3. Распарсить `.dem` через `demoparser2`.
4. Сохранить:
   - агрегированные match metrics в `matches`;
   - полный parsed payload в `matches.raw_json`;
   - служебный manifest с hash/size/source/status;
   - будущие расширенные таблицы по раундам, дуэлям, utility, позициям и таймингам.
5. Проверить, что payload достаточен для повторного анализа без raw `.dem`.
6. Только после проверки удалить raw `.dem`.

## Этап 1: безопасная база для будущего удаления

Реализовать сейчас:

- Страница и API отчета по demo storage.
- Подсчет общего размера `data/uploads`.
- Разделение файлов на:
  - referenced: файл указан в `matches.demo_file` и существует на диске;
  - missing: матч ссылается на файл, которого нет;
  - unreferenced: файл лежит в `data/uploads`, но не привязан ни к одному матчу;
  - suspicious: слишком маленькие `.dem` файлы, которые почти наверняка не являются валидной демкой.
- Список самых больших файлов.
- JSON manifest в `data/reports/demo_storage_manifest.json`.
- Явный флаг политики: raw delete выключен.
- Список кандидатов на будущее удаление: parsed match есть, raw `.dem` существует, но политика удаления пока выключена.
- Никаких удалений.
- Никакой замены `.dem` на архив на этом этапе.

## Этап 2: после согласования метрик

Когда будет утвержден набор метрик и raw-срезов, которые нужны продукту:

- Расширить парсер и сохранить все нужные данные в БД/JSON-артефакты.
- Для каждого матча хранить статус:
  - `raw_demo_kept`;
  - `parsed_payload_verified`;
  - `raw_demo_deleted`.
- Только после этого включать политику удаления исходных `.dem`.

## Будущая схема экономии места по умолчанию

- Удалять raw `.dem` только когда:
  - матч успешно распарсен;
  - нужные метрики сохранены;
  - manifest содержит контрольную запись;
  - есть понятная политика восстановления или повторной загрузки.
- Для dev/debug можно оставить режим удержания raw `.dem` на N дней.
- Для production целевой режим: raw `.dem` удаляется сразу после успешной верификации parsed payload.
- Если понадобится повторный парсинг новыми метриками, до удаления raw надо сначала мигрировать parser payload или временно отключить delete-policy.

## Контрольные записи

Каждое действие по storage должно оставлять след:

- `WORKLOG.md` для инженерного журнала.
- `data/reports/demo_storage_manifest.json` для машинного состояния.
- Не коммитить `data/`, `.env`, демки, refresh tokens и другие секреты.
